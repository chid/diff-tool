Diff Algorithm Performance

Internal learning doc · May 2026 · crates/diff-core

TL;DR: Replaced the default Myers diff engine with Histogram via imara-diff on the pathological test case. Result: 64s → 33s (1.94× speedup). Histogram is now available alongside Myers and Patience via --algorithm.

1. The Problem

The synthetic perf suite revealed a pathological case: many-small-lines-churn — 200,000 lines where every other line is modified ("0", "1-x", "2", "3-x", …). The initial baseline run with the Myers algorithm clocked in at ~64 seconds, making it the dominant perf bottleneck in the entire engine.

CaseLinesAlgoDurationThroughput
sparse-edits-100k-lines100K Myers 23.9 ms87.0 MB/s
tail-edit-10mb250K Myers 108 ms171 MB/s
many-small-lines-churn200K Myers 64,056 ms 0.04 MB/s

Why so slow? Myers' diff is O(ND) where D is the edit distance (number of changes). In the churn case, half the lines change — D ≈ 100,000. The algorithm's dynamic programming table explodes quadratically.

2. Profiling Methodology

Before guessing, we built a Rust micro-benchmark that timed each phase of compare_texts in isolation on the 200K-line churn fixture:

Phase 1 - TextDiff::from_lines + collect: 63.100s  (99.94%)
Phase 2 - Build Vec<LineChange>:              0.004s  ( 0.01%)
Phase 3 - compute_intraline_spans:            0.003s  ( 0.00%)
Phase 4 - build_hunks:                        0.029s  ( 0.05%)
────────────────────────────────────────────────────
Total:                                        63.136s
Key insight: The diff algorithm itself is 99.94% of the cost. Hunk generation, intraline spans, and line-change construction combined take under 4 ms. Any optimization outside the core diff engine would be wasted effort.

3. Algorithms Evaluated

All three algorithms produced identical stats (100K additions, 100K deletions, 100K unchanged). The results on the pathological 200K-line churn case:

Myers
64s
Patience
76s
Histogram
33s

3.1 Myers — O(ND) via similar

64s. The baseline. Optimal edit script, compact diffs, but pathologically slow when D is large.

3.2 Patience — via similar

76s — worse than Myers. Patience is O(N log N) on unique lines but degrades when lines are mostly numeric strings with many duplicates (our churn fixture generates "0" through "199999" — all unique). The overhead of building the LCS table on 200K unique lines dominates.

3.3 Histogram — via imara-diff ✓ winner

33s — 1.94× faster than Myers. Histogram is a variant of Patience that uses a frequency map to prune the LCS candidate set, making it much faster on large inputs with many unique lines. This is the algorithm git diff defaults to since Git 2.0.

imara-diff (v0.2.0) provides a native Rust Histogram implementation via a Diff::compute(Algorithm::Histogram, &input) API. Its hunks iterator returns non-overlapping before/after ranges that map cleanly to our LineChange model.

Beyond the pathological case, Histogram is faster across the board:

Observation: whitespace-only-churn sees an 8× speedup because whitespace normalization reduces many lines to identical strings, which Histogram's frequency pruning handles extremely well. Myers still pays O(ND) for each distinct whitespace-normalized line.

5. Key Learnings

  1. Profile before optimizing. Our initial intuition was that compute_intraline_spans or build_hunks might be the bottleneck — they weren't. The 4 ms combined cost is invisible next to the 63s diff engine.
  2. Patience ≠ fast. Patience is O(N log N) on unique lines. When every line is unique (as in log files or our numeric fixture), the LCS table overhead dominates and it can be slower than Myers.
  3. Histogram is the real deal. By using a frequency map to prune candidates, Histogram avoids Patience's degenerate case while retaining its O(N log N) asymptotic behavior. This is why Git switched to it as the default.
  4. Algorithm pluggability is cheap. Adding a new algorithm required ~100 lines of adapter code in build_changes_imara(). The DiffAlgorithm enum and --algorithm CLI flag make future experiments trivial.
  5. Synthetic fixtures catch real problems. The many-small-lines-churn case was explicitly designed to stress the engine. Without it, we'd ship a tool that hangs for a minute on files with many scattered edits.

6. Architecture

The diff algorithm is selected via a DiffAlgorithm enum in the request model: 

pub enum DiffAlgorithm {
    #[default]
    Myers,      // similar crate, good for normal files
    Patience,   // similar crate, best on unique-line files
    Histogram,  // imara-diff crate, best for large/scattered edits
}

compare_texts dispatches to either the similar path (Myers/Patience via TextDiff::configure().algorithm()) or the imara-diff path (Diff::compute(Algorithm::Histogram, &input)). The output Vec<LineChange> is identical in structure — both paths feed into the same hunk builder and intraline span annotator.

CLI users select the algorithm with --algorithm <name>:

$ dt diff left.txt right.txt --algorithm histogram
$ dt diff left.txt right.txt --algorithm patience
$ dt diff left.txt right.txt                  # defaults to myers

The perf suite (scripts/measure-performance.mjs) now benchmarks both Myers and Histogram for all test cases, doubling the comparison data each run.

7. Recommendations

  • Switch the default to Histogram. It's faster in every synthetic case and matches git diff's default. Myers should remain available for cases where a minimal edit script is preferred over speed.
  • Add a timeout/deadline. Even Histogram at 33s is too slow for interactive use. similar supports a deadline() config that returns a best-effort diff after a time budget. Consider wiring this into DiffRequest.
  • Add peak memory measurement. The perf suite currently tracks wall-clock time and throughput. Large diffs can consume 100s of MB; tracking RSS would catch memory regressions.
  • Consider imara-diff's Myers implementation. imara-diff also provides Myers — it may be faster than similar's. Worth benchmarking on the same fixtures.
