1. What Makes Office Diffing Hard

A .docx file isn't a document — it's a ZIP archive of XML files. A single visible change like "make this word bold" can touch 3+ XML elements across the content model, run properties, and style definitions. This makes diffing fundamentally different from plain text.

Key challenges identified through research and implementation:

ChallengeWhy It's Hard
Formatting vs contentBold→Normal changes no visible text — must diff XML properties, not just extracted text
Tracked changes<w:ins> / <w:del> tags from prior editing create ghost content
Nested runsOne paragraph can have 10+ <w:r> elements — diffing at paragraph level is too coarse
TablesCells contain full paragraphs — structure and content are entangled
CommentsStored in separate comments.xml, linked via IDs — must be diffed separately
Floating point (Excel)1.2 stored as 1.200000000000001 triggers false diffs
Attribute orderingXML attributes reordered = semantically identical, textually different
Embedded mediaNested ZIPs inside the ZIP — want hash-compare, not text-compare

2. OOXML Structure in 60 Seconds

Every .docx is a ZIP with this structure:

archive.zip/
├── [Content_Types].xml          ← MIME types for each part
├── _rels/.rels                  ← Package-level relationships
└── word/
    ├── document.xml             ← THE main content
    ├── styles.xml               ← Style definitions
    ├── comments.xml             ← Comments (linked by ID)
    └── media/                   ← Embedded images/video

Inside word/document.xml, content lives in a deeply nested hierarchy:

<w:document>
  <w:body>
    <w:p>                          ← Paragraph
      <w:r>                        ← Run (text span with uniform formatting)
        <w:rPr><w:b/></w:rPr>    ← Run properties (bold)
        <w:t>Bold intro</w:t>     ← Actual text
      </w:r>
      <w:r>
        <w:t> then normal.</w:t>   ← Another text span
      </w:r>
    </w:p>
    <w:tbl>                        ← Table
      <w:tr>                       ← Row
        <w:tc><w:p>...</w:p></w:tc> ← Cell (contains full paragraph!)
      </w:tr>
    </w:tbl>
  </w:body>
</w:document>

Key insight: Every formatting change forces a new <w:r> (run). A single sentence can span multiple runs. This is why diffing at the paragraph level is insufficient — you must understand the run structure.

3. Three Diff Approaches

We researched and implemented all three approaches in Rust. Each produces runnable diff output from real .docx files.

📝 Approach 1: Convert-to-Text Simple

word/extract.rs :: extract_text()

Walk XML tree, collect all <w:t> text, flatten paragraphs to newline-separated lines, feed into diff-core.

  • ✓ ~50 lines of code
  • ✓ Reuses battle-tested diff-core engine
  • ✓ Single XML pass — fast
  • ✗ Formatting changes invisible
  • ✗ Lost structure (tables, headings)
  • ✗ Tracked changes show as content

Best for: Quick "what text changed?" preview, git integration

🌲 Approach 2: XML Tree Diff Medium

word/xml_diff.rs :: compare_xml_trees()

Flatten both XML files into event streams, walk in lockstep, report every structural difference.

  • ✓ Full XML visibility — nothing missed
  • ✓ Formatting changes detected
  • ✓ Works for any OOXML part file
  • ⚠ Over-sensitive (attribute reordering = false diff)
  • ⚠ Hard to present to users (paths like /w:document/w:body/w:p[3]/w:r[1]/w:t[1])
  • ✗ No semantic grouping — text + formatting = 2 diffs

Best for: Debugging the semantic parser, validating XML generators

🧠 Approach 3: Semantic Model Recommended

word/compare.rs :: compare_documents()

Parse XML into structured WordDocument model with paragraphs, tables, styles, heading levels. Compare model-to-model.

  • ✓ Most meaningful: "Paragraph 3: text changed from X to Y"
  • ✓ Formatting-aware (bold, italic, heading level)
  • ✓ Table-aware (cell-level comparison)
  • ✓ UI-friendly (feeds directly into React components)
  • ✓ Deterministic JSON — snapshot-testable
  • ✗ More complex implementation (~300 lines)
  • ✗ Format-specific parser per doc type

Best for: Primary diff engine (what users see), AI enrichment

5. Verdict & Recommendation

Use Approach 3 (Semantic Model) as the primary engine

The semantic model produces the richest, most user-friendly output. It correctly handles formatting, tables, headings, and tracked changes — all of which the naive text-extraction approach misses entirely.

Fallback strategy:

  • A3 (semantic) for the primary user-facing diff in all three formats
  • A1 (text) for quick preview mode and git integration (word-to-text filter)
  • A2 (XML tree) for debugging, validation, and automated testing

For now: Only Word (.docx) semantic comparison is wired up in compare_office_files(). PowerPoint and Excel return empty results with "not yet implemented" warnings — waiting for their semantic compare modules.

│   ├── xml_diff.rs     ← A2: compare_xml_trees() (event-stream walk)
│   └── compare.rs      ← A3: compare_documents() (semantic model diff)

└── excel/
    ├── mod.rs

All three approaches share the same XML parsing safety layer (xml_util::create_reader with expand_empty_elements and limited entity expansion). Each approach is independently testable with inline tests.

8. Key Learnings

quick-xml 0.37 quirks

  • No namespace resolution — QName exposes raw bytes only. We check for "w:", "p:", "a:" prefixes via byte comparison. Not ideal, but pragmatic.
  • read_text() consumes the End event — after calling reader.read_text(e.name()), the parser has consumed the closing </w:t>. Any depth counter must be manually decremented (depth -= 1) to stay in sync.
  • Empty elements vs Start+End — with expand_empty_elements = true, <p:ph type="title"/> becomes a Start event + End event pair, not an Empty event. This is critical for attribute parsing.

Depth tracking is the hardest part

The most recurring bug class across all extraction modules was mismatched depth counting. The root cause: read_text() and child-function calls both silently consume End events. Lessons:

  • Always decrement depth after read_text()
  • Always decrement depth after a child extraction function returns (it consumed the End internally)
  • Put depth -= 1 before break-condition checks in End handlers
  • Test with tables — they're the best stress test for depth bugs (nested paragraphs inside cells)

Whitespace is tricky

Office XML uses xml:space="preserve" on many elements. We found that trimming <w:t> text caused false diffs when runs within a paragraph needed whitespace between them. Solution: don't trim during text extraction in the shared extractor — only trim at display time in the semantic comparison layer.

Format-specific knowledge is unavoidable

Each Office format uses a different XML namespace (w:, p:, a:, s:) with different element hierarchies. Excel uses a default namespace (no prefix). PowerPoint text lives in <a:t> (DrawingML), not a format-specific element. There is no "generic OOXML parser" that works without format knowledge.
