Research & Implementation Plan

Tree-Sitter Syntax-Aware Diffing

A detailed engineering plan for integrating tree-sitter AST parsing into the diff-tool pipeline — enabling move/rename detection, semantic change classification, and AST-aligned intraline highlights.

Status Investigation Priority P5 (Product USPs) MVP Languages Rust · TypeScript · Python Flag --algorithm syntax
1

Overview & Motivation

Why tree-sitter AST diffing matters for code review

↕

Move & Rename Detection

A function moved within a file currently shows as a full delete + add. Tree-sitter matches subtrees across files — a moved function is tagged moved with a single deletion + addition pair.

◎

Semantic Classification

Each hunk gets a classification: modified, moved, renamed, added, deleted, reformatted. The UI can visually differentiate logic changes from formatting-only noise.

▬

AST-Aligned Intraline Spans

Current intraline spans are naive character prefix/suffix matching. With tree-sitter, changed spans align to AST node boundaries — the highlighted region matches what a developer would consider the "changed token."

2

Pipeline Integration

Where tree-sitter fits in the existing diff flow

Current (line-based) pipeline:
Read files → Binary detect → UTF-8 validate → Normalize endings → Split lines → imara-diff compute → Intraline spans → Build hunks → DiffResult
With tree-sitter (branches at "Split lines"):
Read files → Binary detect → UTF-8 validate → Normalize endings → Split lines →
Line path (default) imara-diff compute → Intraline spans → Build hunks → DiffResult
Syntax path (--algorithm syntax) Parse CST → AST match → Classify changes → Produce hunks → DiffResult

When --algorithm syntax is set, the pipeline branches after line normalization. If the language is unsupported or parsing fails, it falls back silently to the line-based path with a warning. The DiffResult types remain unchanged — only the content and classification of hunks differ.

Algorithm Design

Parsing, bottom-up container matching, and change classification

3.1 Parsing Phase

For each file, detect language from extension, parse with tree-sitter, then flatten the CST into a list of AstNode records. The depth is configurable (--syntax-depth), defaulting to statement level — function defs, class defs, if-blocks, loops — which keeps node count at ~100–500 for a typical file.

AstNode record parser.rs 
struct AstNode {
    id: usize,          // pre-order index
    kind: String,       // "function_definition"
    kind_id: u16,       // numeric kind from grammar
    parent: Option<usize>,
    children: Vec<usize>,
    start_byte: usize,
    end_byte: usize,
    start_line: usize,
    end_line: usize,
    text: String,       // source slice
    hash: u64,          // whitespace-stripped
    named: bool,
}
Language detection parser.rs 
fn language_from_extension(path: &Path)
    -> Option<SupportedLanguage>
{
    match path.extension()?.to_str()? {
        "rs"  => Some(Language::Rust),
        "ts"  | "tsx" => Some(Language::TypeScript),
        "py"  => Some(Language::Python),
        "js"  | "jsx" => Some(Language::JavaScript),
        "go"  => Some(Language::Go),
        "c"   => Some(Language::C),
        // ...
        _     => None,  // fallback to lines
    }
}

3.2 Matching Phase — Bottom-Up Container Matching

Adapted from GumTree's approach. The matching runs in three passes:

Pass 1: Hash-based container matching

Hash every node's content (whitespace-stripped). Group left and right nodes by hash. Where a group has exactly one left and one right node, they match. Walk from leaves upward: if a node's children all match (same count + hashes), the parent is also matched.

Pass 2: Positional heuristic (moves/renames)

For unmatched named nodes, compare ancestry path signatures (e.g. "program > function_definition > block"). If two nodes share the same signature and similar content hash, mark as a probable move or rename.

Pass 3: Bridge fallback

Any remaining unmatched line regions fall through to imara-diff line-based diff inside each unmatched region. This ensures no content is lost even if the AST matching misses something.

3.3 Change Classification

ClassificationDetection Rule
identicalNode matched, no content change
modifiedNode matched, content differs (subtree changed)
movedNode matched, but parent/position changed
renamedNode is a name-bearing identifier that changed
addedNode exists only in right file
deletedNode exists only in left file
reformattedContent identical after whitespace normalization
type_changedNode kind changed (e.g. if → switch)

3.4 Hunk Production

The AST diff produces the same Hunk and LineChange types as the existing pipeline, so no downstream changes are needed. An optional SemanticTag field exposes the classification to the UI:

Implementation Plan

Phased rollout across 5 phases

P0

Dependency Setup

Add tree-sitter, tree-sitter-rust, tree-sitter-typescript, tree-sitter-python to crates/diff-core/Cargo.toml. Create module structure: parser.rs, ast_diff.rs, ast_to_hunks.rs. Add Syntax variant to DiffAlgorithm enum.

P1

Parser Module (parser.rs)

Language enum with grammar lookup. FileLanguage detection from extension (+ --language CLI override). parse_file(text, lang) -> Vec<AstNode> with statement-depth filtering and whitespace-stripped content hashing. Parser reuse via Mutex<Parser> pool. LruCache for repeated parses.

P2

AST Matching (ast_diff.rs)

compute_ast_diff(left, right) -> AstDiff implementing bottom-up hash matching + positional move/rename heuristic + bridge fallback to imara-diff. Output: Vec<NodeMatch> with similarity scores and classifications.

P3

Hunk Production (ast_to_hunks.rs)

Convert AstDiff + source text to Vec<LineChange> and Vec<Hunk>. Set IntraSpan byte ranges from AST node boundaries. Add optional SemanticTag to Hunk.

P4

CLI & Desktop Integration

Add --algorithm syntax, --language <lang>, --syntax-depth <level> CLI flags. Show semantic tags in human-readable output. Desktop gets SemanticTag via IPC automatically — no renderer changes needed.

Benchmark expectations, mitigations, and memory budget

ScenarioLine-BasedAST (statement)AST (expression)

sparse-edits~3ms~50ms~80ms
whitespace-churn~100ms~120ms~140ms
many-small-lines~33s (Histogram)Memory-bound — size gate applies

Mitigations

1

Statement-level default depth

Limits node count to ~100–500 per file instead of thousands of leaf tokens.

2

Deadline cancellation

Existing deadline_ms in DiffRequest applies. If exceeded, fall back to line-based.

3

File size gate

Skip AST parsing for files > 10K lines or > 1 MB. Configurable via --syntax-max-size.

4

Parser reuse & caching

Mutex<Parser> pool avoids re-allocation. LruCache by content hash for repeated parses in folder compare.

Open Questions

Items to investigate during implementation

Does tree-sitter parsing add acceptable overhead for <5K line files? ▾
Run perf suite with --algorithm syntax on all existing cases. Compare wall-clock time and memory against line-based baseline. Acceptable = <2× overhead for <5K line files.
Can whitespace-normalized hashing reliably detect moves/renames? ▾
Fixture: move a function to a different position in the same file; verify it's detected as moved not deleted + added. Test with content changes inside the moved block.
How does node count affect matching time? ▾
Synthetic files with 100/500/1000/2000/5000 statements; measure matching time at each size. Look for O(n²) inflection point.
Does tree-sitter CST handle incremental edits? ▾
Not needed for MVP (we always diff two static files), but relevant for live editing feature. Tree-sitter supports incremental parsing natively — note for future.
What's the memory overhead of loading 3 grammars concurrently? ▾
Profile with heaptrack or jemalloc stats. Each grammar is ~200–500 KB compiled. Load on demand, not at startup.
Can we share a single Parser across rayon threads? ▾
tree_sitter::Parser is not Send. Option: thread-local pool via thread_local! or Mutex<Parser>. Since folder compare diffs files in parallel, each rayon thread needs its own Parser.
Do all 3 MVP grammars compile cleanly on aarch64-macos? ▾
Add them to deps and run cargo build. Tree-sitter grammars use C and may need a C compiler. Verify on CI's macOS ARM runner.

Glossary

CST
Concrete Syntax Tree — the exact parse tree from tree-sitter, preserving all tokens including punctuation.
AST
Abstract Syntax Tree — a simplified CST. Terms used interchangeably in this document since tree-sitter produces a CST that we treat as an AST.
GumTree
A tree-diff algorithm that uses bottom-up container matching and hashing. Our approach is a simplified adaptation.
Named node
A tree-sitter node with a semantic name (e.g. function_definition). Distinguished from anonymous nodes which are syntax tokens (e.g. (, )).
Statement depth
Nodes at the level of statements, function defs, class defs, and block-level constructs. The default granularity for MVP.
Expression depth
Includes expression-level nodes (e.g. binary_expression, call_expression, identifier). More nodes, higher cost.
Token depth
All leaf nodes — every keyword, identifier, operator, and literal. Equivalent to character-level at the extreme end.
